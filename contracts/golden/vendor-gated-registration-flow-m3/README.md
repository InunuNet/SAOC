# Golden: vendor-gated-registration-flow — M3 decision record (Stand Booking Payment)

Mission `vendor-gated-registration-flow`, M3 (F26-F32). Full milestone/feature breakdown
lives in `contracts/contract-vendor-gated-registration-flow.yaml`. This README is the
decision record @dev implements against; @dev may not deviate from a decision recorded here
without flagging it back to the orchestrator. M1's decision record (application/review/token
flow) is `contracts/golden/vendor-gated-registration-flow-f1/README.md`; M2's (full-form
field-set correction) is `contracts/golden/vendor-gated-registration-flow-m2/README.md`; M4's
(human-readable registration code) is `contracts/golden/vendor-gated-registration-flow-m4/README.md`
— unrelated, do not confuse.

## Where M3 sits in the flow

1. Short public application (`vendorApplications`) — M1
2. Committee approves the application → single-use registration code (M4) emailed
3. Vendor claims the code, gets a 30-minute session, submits the full registration form →
   `vendorSubmissions`, `status: 'submitted'`
4. Committee reviews the submission (`app/api/admin/vendors/[id]/review/route.ts`, F6/F8):
   `submitted → under-review → approved | rejected`
5. **← M3 goes here.** On the `approve` transition, a stand-payment link is minted and
   emailed. The vendor pays; the stand is confirmed once the gateway settles.

**Brad's sequencing decision (already made, not open for re-litigation here): payment comes
strictly after the committee approves the completed submission, never before.** The
disqualification-after-payment risk he raised is designed out by this ordering, not
disclosed. Do not build a pay-first path, and do not let any code path accept a payment
against a submission that is not currently `status: 'approved'`.

## The crux decision: a new sibling collection, not the ticket model

**New Firestore collection: `vendorStandOrders`.** One document per vendor submission,
document id **equal to `vendorSubmissionId`** (not an autogenerated id) — see "Why the doc id
is the submission id" below.

```typescript
export type VendorStandBoothSize = 1 | 2 | 3;
export type VendorStandOrderStatus = 'pending' | 'paid' | 'failed' | 'cancelled';

export interface VendorStandOrder {
  id: string; // == vendorSubmissionId
  vendorSubmissionId: string;
  businessName: string;     // denormalized snapshot, for gateway display + admin visibility
  contactEmail: string;     // denormalized snapshot, for gateway display + confirmation email
  boothSize: VendorStandBoothSize;
  amount: number;           // server-derived ZAR, NEVER client-supplied
  status: VendorStandOrderStatus;
  gateway: string;          // resolved from adminSettings/activePaymentGateway at initiate time
  gatewayPaymentId: string | null;
  standOrderRef: string;    // `VSO-{vendorSubmissionId}`, echoed to the gateway as its reference
  createdAt: Date;
  paidAt: Date | null;
  failedAt: Date | null;
}
```

**Why NOT `orders`/`tickets`.** A vendor paying for a stand is not an attendee buying
admission. Reusing the ticket model would force every field that doesn't apply — attendee
name/email (a business isn't an attendee), `ticketType` (there is no admission product; a
booth size is not a Sanity `ticketType` doc), `chosenDay`, capacity/`releasedQuantity`
(a booth allocation isn't a seat-limited pool the way a ticket type is), and would put
vendor money in the same collection `reconcile-orders`, the door check-in scanner, and every
`orders`/`tickets` query already walks — meaning every one of those surfaces would need a new
"and also exclude vendor rows" filter it doesn't have today, or silently misbehave (a stand
order showing up as a strandable "reserved" order with no expiry policy that makes sense for
it, or a vendor's booth confusingly appearing in a door check-in report). A sibling collection
with its own status vocabulary and its own reconciliation posture (see "No `'reserved'`
status — deliberately" below) keeps blast radius zero on every existing ticketing surface.
This is a structural decision, not a naming one — do not fold `VendorStandOrder` fields onto
`Order`/`Ticket` "to save a collection."

**Relationship to F7's existing manual payment fields.** `VendorSubmission` already carries
`proofOfPaymentPath`/`proofOfPaymentUploadedAt` (public upload) and
`boothNumber`/`paymentReceived`/`paymentConfirmedBy`/`paymentConfirmedAt` (office-use, set by
`lib/vendor-payment.ts`'s `decideVendorPaymentUpdate()` via the capability-gated admin route)
from F7. **M3 is additive to F7, not a replacement.** F7's manual path stays live — a vendor
who pays by EFT/bank transfer off-platform still needs a way to be marked paid by an
operator. M3's gateway-settlement route additionally sets `VendorSubmission.paymentReceived =
true` on success (see "Settlement" below), through the SAME field F7 already owns, so the
admin list shows one paid/unpaid signal regardless of which path produced it. `boothNumber`
allocation stays a manual admin action (F7, unchanged) — M3 has no opinion on booth
*numbering*, only on booth *fee collection*.

**FLAGGED AMBIGUITY, not resolved here:** whether Council wants the manual EFT/proof-of-upload
path (F7) retired once M3 ships, or intentionally kept as a second acceptable payment method.
Nothing in Lee-Ann's source doc says "gateway-only." Recommend: keep both, label them
distinctly in the admin UI ("Paid via gateway" vs "Paid — office confirmed manually") so an
operator never conflates the two. This is a product decision for Brad/Council, not an
engineering one — do not silently retire F7's route.

## No `'reserved'` status — deliberately

Tickets use `'reserved'` because a ticket type has finite capacity that must be held (and
released on expiry) while checkout is in flight. A stand booking has no such pool — nothing
is "held" by a `vendorStandOrders` doc sitting at `'pending'`; the vendor's booth-size choice
doesn't compete with any other vendor's for a shared capacity number this feature manages.
There is therefore no `order-reconciliation.md`-style "stranded reservation" hazard: a
`'pending'` order that never gets paid is not blocking anything, and does not need an expiry
timestamp, a Cloud Scheduler sweep, or a re-alert window. It just... sits unpaid, visible to
admins, until the vendor pays or an operator otherwise resolves it out of band.

## Why the doc id is the submission id (a deliberate simplification over the ticket model)

A vendor may book **exactly one** stand — see "Booth size already encodes the multi-stand
case" below — so there is a permanent 1:1 relationship between `vendorSubmissions/{id}` and
`vendorStandOrders/{id}`. Making the stand-order doc id literally equal to the submission id
means:

- **Initiate** is a single-document read-check-write inside one transaction (same shape as
  `lib/vendor-registration-token-claim.ts`'s `claimRegistrationToken()`), never a `.where()`
  query — there is no race window between "check if an order already exists for this
  submission" and "create it."
- **Settlement** parses `vendorSubmissionId` directly out of `standOrderRef` (fixed `VSO-`
  prefix) and resolves `vendorStandOrders.doc(vendorSubmissionId)` directly — no index query
  at all, unlike `markOrderAndPositionPaidByPaymentId`'s `m_payment_id` query fallback (that
  fallback exists there because one buyer can create many orders over time; a vendor cannot
  create a second stand order once one exists for their submission).

This is a genuine, deliberate departure from the ticket model's `m_payment_id`-keyed-by-query
pattern — record it as such, don't "fix" it to look more like tickets' code.

## Booth size already encodes the multi-stand case — no line items, no quantity field

The 26 Aug source doc's three booth options are not "N booths of a chosen size" — they ARE
the multi-stand cases:

```
1  Single Booth  – 2.5m x 3m
2  Booths (Double) – 5m x 3m
3  Booths (Triple) – 7m x 3m
```

Option 2 IS "two booths, combined into one 5m×3m footprint." Option 3 IS "three booths,
combined into one 7m×3m footprint." Lee-Ann's voice note that "most invited vendors have
already asked for two or three" stands is satisfied by the vendor picking option 2 or 3 — it
is a single selection, not a cart with a quantity. **`VendorStandOrder.boothSize` is a single
`1 | 2 | 3` value. Do not add a quantity field, do not build a multi-line-item cart for this
(F4's `ticketing-multi-line-item-cart` machinery is the wrong shape here — do not reuse it).**

## Relationship to M2/F17 (not yet shipped) — M3 does not depend on it

F17 (`vendor-gated-registration-flow-m2`, `status: pending`, not yet implemented as of this
writing) plans to add a `boothSize` radio group to `VendorBoothFieldset.tsx`, replacing the
scalar `boothCount` number input on `VendorSubmission` itself, using these same three labels.
**M3 deliberately does NOT wait for F17 and does NOT read a `boothSize` field off
`VendorSubmission`.** Instead, the payment page (F29) collects the booth-size choice itself,
independent of whatever the registration form does or doesn't capture. Reasons:

1. F17 is unbuilt; M3 cannot safely assume a field that doesn't exist yet on the type.
2. Payment is the natural checkout moment to confirm what's being bought — a vendor should be
   able to change their mind about size between submitting the form and paying (the two are
   days apart, via committee review) without it becoming a form-resubmission.
3. Pricing must never be authoritative from an optional, submitter-supplied form field even
   after F17 ships — the amount is *always* re-derived server-side from what the vendor
   selects **at payment time**, on the payment page, checked against the closed `{1,2,3}` set.

**If F17 ships later:** `VendorSubmission.boothSize` becomes pre-fill/display data only (e.g.
"you told us on the form you wanted a double booth — confirm below"), never the source of
truth for the amount charged. Do not wire it to bypass the payment page's own selection.

## The missing-figure problem — genuinely worse than "one blank cell"

The brief's framing ("the document leaves the stand fee blank") undersells it: the 26 Aug
source doc's own changelog states the standalone **"Booth Fees & Payment" section was REMOVED
entirely** between the 25 Aug and 26 Aug revisions (see
`docs/leeann-source/2027-vendor-registration-form_2026-08-26.md` lines 15-17). The 26 Aug doc
contains **zero rand figures for booth size fees anywhere** — not even a `R…..` placeholder.
The only `R…..` placeholders that exist in the canonical doc are for **tables/chairs**
("at an additional charge of R ….. per table and R ….. per chair", line 131) — a genuinely
separate, second missing number that M3 does not attempt to charge for at all (see "Tables
and chairs are out of scope" below).

Per the mission's hard constraint, `lib/vendor-stand-pricing.ts` is the SOLE source of truth
for the three booth-size prices, and every value starts `null`:

```typescript
export const VENDOR_STAND_BOOTH_SIZES = [1, 2, 3] as const;

// Council-blocked. Every value is null until the Show Organising Committee confirms a real
// ZAR figure per booth size — see the golden README's "The missing-figure problem". Do NOT
// fill these with an invented or estimated number, unlike lib/provisional-figures.ts's
// flagged-provisional pattern (that pattern is for numbers this project chose to estimate and
// disclose; there is no estimate to disclose here — the source document has no number at all
// to anchor an estimate to).
export const VENDOR_STAND_PRICE_ZAR: Record<(typeof VENDOR_STAND_BOOTH_SIZES)[number], number | null> = {
  1: null,
  2: null,
  3: null,
};

export type VendorStandPriceResolution =
  | { ok: true; amount: number }
  | { ok: false; reason: 'not-configured' | 'invalid-booth-size' };

// Never throws, never guesses, never falls back to a default price — same posture as
// resolveActiveGateway(). A caller that mistook "not yet priced" for "assume some figure" is
// exactly the defect this exists to rule out.
export function resolveVendorStandPrice(boothSize: unknown): VendorStandPriceResolution { /* ... */ }
```

**Milestoning the missing figure — this is the "something demoable early" answer for M3.**
F26-F32 ship the ENTIRE payment mechanism end-to-end, fully wired to the real gateway
abstraction, right now — token mint/email on approval, the payment page, the initiate route,
the idempotent settlement webhook, admin visibility. It refuses at the one point where a real
number is missing: `POST /api/vendors/stand-payment/initiate` calls
`resolveVendorStandPrice(boothSize)` and returns `HTTP 503` with `{ error: "Stand pricing has
not yet been confirmed by the Show Organising Committee. Payment is not available yet." }`
when the result is `not-configured` — **before** calling the gateway, before creating any
`vendorStandOrders` document. The moment Council supplies three real numbers, filling in
`VENDOR_STAND_PRICE_ZAR` is the entire follow-up change — no route, no page, no token logic
touched. A55 (below) proves this transition behaviourally: the same initiate call refuses
with prices null and succeeds with prices set, using the real route via the harness.

## Tables and chairs are out of scope for M3

The source doc's separate `R…..`-per-table/`R…..`-per-chair charges (already council-blocked
and already flagged by F17's own note in the M2 contract: "council-blocked, do not invent a

## The 90-day forfeiture notice — where it lives, and why that's not "in the T&Cs"

F20 (M2, not yet shipped) already plans to embed the verbatim 14-clause T&Cs block —
including the written 90-day cancellation clause — into the *registration form itself*, which
the vendor accepts days or weeks before they ever see a price. Brad's ask for M3 is a second,
independent placement: **stated plainly on the payment page, before the vendor pays** — the
moment money is actually about to move, not buried in a document they agreed to earlier.

`lib/vendor-stand-forfeiture-notice.ts` exports one constant, quoting both operative sentences
from `docs/leeann-source/2027-vendor-registration-form_2026-08-26.md` lines 242-243 verbatim
(not paraphrased):

```typescript
export const VENDOR_STAND_FORFEITURE_NOTICE =
  'All vendor registrations and payments must be finalised no later than 90 days before the ' +
  'opening of the show. Cancellations received within 90 days of the show will not qualify ' +
  'for a refund.';
```

The payment page (F29) renders this string, sourced ONLY from this constant (never
retyped inline in JSX — see A56's "single source" check), in a visually distinct notice block
that precedes the "Pay Now" / gateway-redirect control in DOM order. This is a structural
placement requirement, not a money-handling one, so a source-order/rendered-HTML assertion
(same technique as A9/A52's real `react-dom/server` renders) is sufficient — it does not need
the harness the way the amount/idempotency assertions do.

**Do not resolve the voice-note-vs-written-doc "2 months" vs "90 days" contradiction by
splitting the difference or picking the friendlier number.** The written document — what the
vendor actually reads and pays against — is binding. This was already decided in M1/M2's
decision record; M3 only adds where the same figure gets displayed, not a new number.

## Token mechanism — new trust domain, state-gated not single-use

`lib/vendor-stand-payment-token.ts`, structurally identical to `lib/vendor-registration-token.ts`
(HMAC, `${base64url(JSON.stringify({s: vendorSubmissionId, e: expiresAtEpochMs}))}.${hmacHex}`
— payload key `s`, a THIRD distinct key alongside M1's `a` and the order-recovery token's `o`,
for the same structural-domain-separation reason M1's doc gives). New env var
`VENDOR_STAND_PAYMENT_TOKEN_SECRET` — never shared with `VENDOR_REGISTRATION_TOKEN_SECRET` or
`RECOVERY_TOKEN_SECRET`. Default TTL 30 days
(`VENDOR_STAND_PAYMENT_TOKEN_DEFAULT_TTL_MS`) — long enough for slow committee-to-vendor
turnaround and a lapsed-attention vendor, unlike the registration code's tight 30-minute
session.

**Unlike M1's registration token, this token is NOT single-use.** A vendor may need to reload
the payment page, retry after a failed gateway attempt, or return days later having gotten
distracted. The token has ZERO authorization meaning beyond "cryptographically valid and not
expired" — exactly M1's own stated posture — and **every use site (page-level AND route-level)
re-verifies the linked submission's CURRENT state before acting**, never trusting a state
snapshot from mint time:

- Refuse (generic message, never distinguishing the reason — same enumeration-blindness
  posture as M1's register route) if the submission does not exist, is not currently
  `status: 'approved'` (covers `rejected`, and covers the residual case where a submission was
  approved, then a later admin action somehow changes it — defence in depth), or if its
  `vendorStandOrders` doc already has `status: 'paid'`.
- This means a submission that was `approved` when the token was minted but is (hypothetically)
  no longer `approved` by the time the vendor clicks pay is refused at that moment, not at mint
  time — the token being cryptographically valid proves nothing about eligibility to pay,
  identical in spirit to M1's "zero authorization meaning" token design.

## Approval triggers the mint (extends F6/F8's existing route, not a new admin action)

`app/api/admin/vendors/[id]/review/route.ts`'s existing `'approve'` action (F6, decision logic
in `lib/vendor-review.ts`, unchanged) already sends F8's approval confirmation email strictly
after the 3-key status-transition write commits, via `deliverConfirmationEmailAfterCommit()`.
M3 adds a SECOND post-commit, non-blocking step to that same hook: mint the stand-payment
token and send a new email (`emails/VendorStandPaymentReady.tsx`, via a new
`lib/vendor-stand-payment-notice.ts` sender) containing the link to
`/national-show/vendors/payment?token=...`.

**Deliberately NOT fail-closed the way M1's application-approval token mint is.** M1's mint
happens BEFORE the application's status-transition write, so a missing secret leaves the
application safely `pending` and recoverable. Here, the submission's `approved` status is
already committed (F6's own transition, unrelated to payment) by the time M3's mint runs —
gating the SUBMISSION approval itself on the PAYMENT token secret being configured would wrongly
couple two independent admin decisions. Instead, this follows F8's own already-established
posture for this exact route: **the approval write commits regardless of what happens next; a
downstream notification failure is logged and non-fatal, with an operator escape hatch.**

**The escape hatch, so a lost/failed email doesn't strand an approved vendor with no way to
pay:** `POST /api/admin/vendors/[id]/resend-payment-link`, gated identically to the review
route (`getAdminSession()` → `hasCapability(..., 'review-vendor-applications', ...)`),
callable any time the submission is currently `status: 'approved'` and its stand order (if any)
is not yet `'paid'`. Mints a fresh token, re-sends the email. This is the same "reissue, not
unlock" shape F25 (M4) already established for the registration code — do not build a
separate "view the existing link" mechanism; always mint fresh.

## Initiate — server-derived amount, transactional idempotency

`POST /api/vendors/stand-payment/initiate`, body `{ token, boothSize }`.

1. Verify the token (`verifyVendorRegistrationToken`-equivalent for this new module). Invalid
   → generic 403, same posture as M1.
2. Re-read `vendorSubmissions/{vendorSubmissionId}` (id from the verified token payload).
   Refuse (403, same generic message) unless `status === 'approved'`.
3. Validate `boothSize` is one of `{1,2,3}` (reject anything else, including a value that
   happens to already be numerically `1|2|3` but arrives as a string, `NaN`, or out of range).
4. `resolveVendorStandPrice(boothSize)` — `HTTP 503` with the council-blocked message on
   `not-configured` (see above). **This is the ONLY source of `amount` — the request body
   never carries an amount field, and if it did, it would be ignored, mirroring how the
   ticket checkout route already ignores a client-sent `providerId` today.**
5. `resolveActiveGateway()` — `HTTP 500`, same message shape as the ticket checkout route's
   existing gateway-not-configured refusal, if unset.
6. `resolveProvider(gateway).readiness('initiate')` — refuse (same message shape as the
   ticket checkout route) if not ready.
7. Inside ONE Firestore transaction on `vendorStandOrders.doc(vendorSubmissionId)`: re-read;
   if it exists and `status === 'paid'`, refuse ("This stand has already been paid for.");
   otherwise `.set()` (create-or-overwrite) the doc with the freshly-derived `boothSize`,
   `amount`, `gateway`, `standOrderRef: 'VSO-' + vendorSubmissionId`, `status: 'pending'`,
   `createdAt: now`, `paidAt: null`, `failedAt: null` — a re-initiate (retry, or vendor
   changed their mind about size before paying) legitimately overwrites the prior pending
   attempt; a paid one is immutable through this path.
8. Call `provider.initiate({ reference: standOrderRef, amountFormatted: amount.toFixed(2),
   itemName: 'SAOC National Show — Vendor Stand (' + businessName + ')', returnUrl,
   cancelUrl, notifyUrl })`. Return the redirect fields to the client, same response shape the
   ticket checkout route already returns.

## Settlement — one shared handler, two thin per-gateway routes, full idempotency

`POST /api/vendors/stand-payment/payfast-itn` and `POST /api/vendors/stand-payment/ozow-itn`
are thin pass-throughs (same shape as `app/api/tickets/itn/route.ts` /
`app/api/tickets/ozow-itn/route.ts`) naming exactly one provider each, both calling a shared
`lib/vendor-stand-payment-notification.ts` handler (mirrors `lib/tickets-notification.ts`'s
shape).

The handler:

1. `provider.verifyNotification(request)` — signature check. Invalid → log, `200 OK` with no
   state change (same "don't tell an attacker which check failed by status code" posture the
   ITN route already uses).
2. Parse `vendorSubmissionId` out of `notification.reference` (strip the `VSO-` prefix;
   malformed/missing prefix → log, no-op, same as above).
3. Inside ONE Firestore transaction touching BOTH `vendorStandOrders.doc(vendorSubmissionId)`
   and `vendorSubmissions.doc(vendorSubmissionId)`:
   - Re-read the stand order. Missing → no-op (logged).
   - **Cross-gateway guard**: refuse (logged, no state change) unless
     `order.gateway === provider.id` — a payfast notification must never settle an order
     created under Ozow or vice versa, identical reasoning to
     `markOrderAndPositionPaidByPaymentId`'s `expectedGateway` check.
   - **Idempotency**: if `order.status !== 'pending'` (already `'paid'`, or `'failed'`/
     `'cancelled'` from a prior explicit failure), no-op and return success — a duplicate or
     replayed notification for an already-settled order changes nothing and is not an error.
   - **Amount guard**: refuse (logged, no state change, order stays `'pending'`) unless
     `notification.grossAmountCents === Math.round(order.amount * 100)` — the stored,
     server-derived amount is the ONLY thing ever compared against; the notification's amount
     is never written anywhere as authoritative.
   - On every check passing: `transaction.update(standOrderRef, { status: 'paid', paidAt: now,
     gatewayPaymentId })` AND `transaction.update(submissionRef, { paymentReceived: true })` —
     one atomic pair, both-or-neither, same reasoning as `writeReservationPair`.
4. `mapStatus`/failure notifications (`'failed'`, `'cancelled'`) follow the same transaction
   shape but write `status: 'failed'`/`'cancelled'` + `failedAt`, never touching
   `vendorSubmissions.paymentReceived`.

**A55-A58 below prove this behaviourally via the route-runner harness** — Codex's own finding
against this mission's A50 (a source-order check that passed over a real defect the
behavioural harness caught) is exactly why "the ITN route reads the right field" is not
sufficient; the assertions must exercise the real transaction with two concurrent/duplicate
notifications and a tampered amount, not just read the source for the right function calls.

## Admin visibility (F32) — read-only, no new "mark paid" button

`/admin/vendors` (existing submission list/detail) gains a read-only stand-payment status
badge, driven by a Firestore read of `vendorStandOrders/{id}` alongside the existing
submission query — `Not started` / `Pending` / `Paid` / `Failed`. **No admin action sets
`vendorStandOrders.status` to `'paid'`.** Per the mission's standing security condition, only
the gateway settlement handler may do that — an admin "mark paid" button here would be exactly
the "vendor/operator can mark themselves paid" hole the mission explicitly rules out for the
*gateway* path. (F7's separate manual `paymentReceived` toggle for the EFT path is unaffected
and stays exactly as it is — that path was always operator-attested, by design, for a payment
this codebase cannot itself verify.)
