  Verified: changing SUNSET_COCKTAILS_SINGLE_PRICE from 800 to 700 left A7 green because
  `capacity: 800` elsewhere in the file still satisfies the numeric grep.

A11 — `grep -q "data-placeholder" components/tickets/TicketTypeCard.tsx` is a static grep
  that matches the string appearing anywhere in the file (variable name, comments), not
  proof that the attribute is actually attached to the rendered root element when
  `provisional === true`. Verified: setting `placeholderAttrs = {}` unconditionally (so the
  attribute is NEVER attached) left A11 green, because the identifier `placeholderAttrs`/
  comment text still contains the substring "data-placeholder".

A15 — `grep -oE "name: '(SAOC Symposium|WOSA Conference|SAOC/WOSA Joint)"` counts DISTINCT
  MATCHED PREFIXES, not occurrence counts or product identity. Verified: adding a genuinely
  new 4th conference product whose name happens to start with one of the three allowed
  prefixes (e.g. "WOSA Conference Extra Track") does NOT change the distinct-prefix count
  and so does not fail A15, even though it is exactly the "a fourth family" defect A15's own
  description says it guards against. A prefix collision, not a name-identity check, would
  slip through undetected.

Both weaknesses fall in this project's own previously-audited "assertion satisfiable by
something that isn't the real property" defect class (see workflow.md's Codex-review
rationale). The implementation itself is correct against the golden decision records; these
are reported as contract-quality findings, not implementation gaps.

## Follow-up: setIfMissing vs present-and-null hazard (raised by team lead 2026-09-08)

Question: does `category: null` in the original audit's GROQ output mean the field is
genuinely ABSENT (setIfMissing correct) or PRESENT-and-null (setIfMissing would silently
no-op)? GROQ's plain field projection returns `null` for both cases indistinguishably.

New file: `scripts/f2-diagnose-category-field.ts` — READ-ONLY (only `client.fetch()`, no
`.patch()`/`.commit()`/`.create()`/`.delete()` anywhere in the file). Checked two independent
ways against the live "production" dataset:

1. `defined(category)` via GROQ — false for all 5 documents checked (4 admission SKUs +
   early-bird-weekend-pass cross-reference). Per Sanity's own semantics this alone does NOT
   distinguish absent from present-null (both give `defined() == false`) — reported as a
   cross-reference only, not the answer.
2. Raw document JSON (no field projection) inspected in JS via
   `Object.prototype.hasOwnProperty.call(doc, 'category')` — this DOES distinguish the two
   cases, since a present-but-null field would still appear as an object key in the raw doc.

Result (exact output):
  ticketType-early-bird: category is ABSENT
  ticketType-day-visitor: category is ABSENT
  ticketType-weekend-pass: category is ABSENT
  ticketType-vip: category is ABSENT
  ticketType-early-bird-weekend-pass: category is ABSENT

Conclusion: `category` is genuinely absent, not present-and-null, on all 4 documents the
migration's category-patch ops target. `setIfMissing` is correct and the more conservative
choice — kept as-is, not changed to `set`. Recorded this confirmation inline in
`buildMigrationPlan()`'s comment (scripts/migrate-f2-ticket-taxonomy.ts) so a future reader
sees it was checked, not assumed.

Also strengthened `runVerify()` (same file) per the team lead's 3rd requirement: it now
compares the ACTUAL post-apply field values against the plan's intended values for every op
kind (previously the `create` branch only checked `doc != null`, which would pass even
against a document created with wrong price/category/active — now checks
`price`/`category`/`active` match; `price-patch` now also checks `sourceCitation` landed).
A verify run against an untouched dataset will report MISMATCH for every op, not a false OK.
