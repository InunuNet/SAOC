=== Real bugs found and fixed during F7 build (harness bugs, not contract deviations) ===
1. playwright.config.ts cannot use a top-level `await` while the repo has no
   `"type": "module"` in package.json (changing that repo-wide was out of scope) --
   config.ts loads as CommonJS and top-level await threw "ReferenceError: await is not
   defined". Fixed by building the whole config in an async function and exporting the
   resulting Promise; Playwright's config loader awaits a Promise-shaped default export.
2. Each Playwright worker process re-`require()`s playwright.config.ts. A naive
   `await getFreeLocalPort()` on every load handed the main process (which starts
   `webServer`) one port and each worker (which sets `use.baseURL`) a DIFFERENT port --
   every nav test failed with ERR_CONNECTION_REFUSED even though the dev server was
   genuinely running, just on a different port than the test was hitting. Fixed by
   caching the discovered port in `process.env.SAOC_E2E_DYNAMIC_PORT` on first
   computation; worker processes inherit the parent's environment.
3. Using `127.0.0.1` (not `localhost`) as the base URL tripped Next 16's
   `allowedDevOrigins` cross-origin dev-request guard on the HMR websocket
   (`next.config.ts` only allowlists this project's own secure local dev hostname).
   The blocked HMR socket caused the Next dev client to force full-page reloads mid-test,
   silently wiping typed form values and the pending click before the real submit ever
   fired -- contact-form-mocked.spec.ts failed with no request ever reaching the mocked
   route, and no visible error state either (the reload raced with the assertion).
   Diagnosed with a throwaway instrumented Playwright script (not committed) logging
   console/network events, which showed the "Download the React DevTools" message
   logging twice per page visit (i.e. two full loads) and the WS handshake failing with
   net::ERR_INVALID_HTTP_RESPONSE. Fixed by using `localhost` for the harness's base URL
   instead of the loopback IP -- zero changes to next.config.ts (contract-owned, out of
   scope for F7).
4. Next's dev-server lock (`.next/dev/lock`) is scoped to the PROJECT DIRECTORY, not to
   the port -- running a second `next dev` (even on a different port) against the same
   checkout fails immediately with "Another next dev server is already running." This
   collided repeatedly with other agents' concurrently running dev servers during this
   session (expected, per the brief's own "other agents are working concurrently... is
   a collision, retry" note) and is worth flagging: any CI or local run of this harness
   will fail outright if something else already has `next dev` open against this exact
   checkout, regardless of the dynamic port scheme -- the dynamic port protects against
   PORT collisions, not against this directory-level lock. Not fixed (out of scope --
   this is Next's own behavior, not a bug in the harness), but worth the team's
   awareness: CI runners are single-checkout-per-job so this won't bite there; it can
   bite two agents developing in the same local checkout simultaneously.
