## 1. How the default gate decides what runs (execution/contract.py, read-only)

- There is no `manual_only`, skip flag or kind that excludes a shell assertion. `normalize_contract` (`execution/contract.py:68`) turns every `assertions.checks` entry into a shell assertion (`kind: shell`, line 161 `check_type = check.get("type","shell")`); the only recognised per-check keys are `type` (codex_qa, browser_deployed_check, gws_inbox_check), `timeout_seconds`, `required`, `phase`, `command`. An unknown key such as `manual_only: true` on a check is silently dropped (lines 161-195).
- A top-level `manual_only:` block survives `c = dict(contract)` but no code path reads it (grep `manual_only` in `execution/contract.py` is empty), so it never becomes an assertion. Probed: `contract.py validate --strict` and `gate --phase 4 --run-checks` on a contract carrying that block pass and run only `assertions.checks`.
- Phases: `gate --phase N` runs only phase N (`_gate_dispatch`, line 1052), but `--phase all` runs every phase (line 1056) and `mission.py:1341` defaults milestones to `["all"]`; `improvement_loop.sh:243` also uses `--phase all`. `--phase max` runs only the highest phase (1079). So a per-check `phase:` (line 150, GH #1317) is not a safe parking place: it is still run by `all`, and a high phase hijacks `max`. `gate_sweep.py:1852` and the quick-gate skill (`.claude/skills/quick-gate/SKILL.md:19`) run phase 4.
- Skips: exit 77 from a shell command is verdict `skip` (line 380); a skip fails the gate unless `--allow-skips` (line 726) and always fails when `required: true` (line 670). A guard that exits 77 therefore turns a default gate red, so it is not a usable `manual_only` mechanism.
- `gate_cmd` (line 1107) runs `scan-dataset-residue.ts` (a Sanity read through `client.fetch('*[]')`, `scripts/scan-dataset-residue.ts:332`) before and after every gate (lines 1122 and the post-flight call); that scan is read-only and fails open.
- `gate_sweep.py` clones the repo per spec for containment, but a clone does not contain network writes: a check that POSTs or patches reaches the live backend from inside the sandbox.

**Consequence for the plan.** The only way to keep a live check out of every gate path is to take it out of `assertions.checks` (and any `phases:` list). The convention this mission introduces: a top-level `manual_only:` list in the same contract file, each entry `{id, description, command, reason}` with an inline reason of at least 40 characters. contract.py ignores it, `validate --strict` accepts it, and the scanner enforces it.

## 7. Ambiguities for the lead

1. Is the local `.env.local` always the production project? Evidence says yes: one Sanity project and dataset (`.env.local.example:26-27` `26yfbug4`/`production`), one Firebase project (`.firebaserc` `saoc-webapp`), and `apphosting.yaml` points the same ids at the deployed app. If a developer points a local `.env.local` at another project the check is harmless there, but the contract cannot know, so it is classed real.
2. Two cache/session effects (`f2-deploy-next16` A9 revalidating the production ISR cache, `admin-settings-deploy-and-chrome-fix-f1` A6 minting a production admin session) leave no dataset residue. Classed REAL_DEPLOYED / REAL_AUTH to follow the rule literally ("nothing that writes to production runs in a gate"). Say if you want them waved through; it is a registry edit.
3. The ticketing-hardening family writes sentinel orders to real Firestore through a local dev server with live `.env.local`. Whether that server also calls Resend for a sentinel order is not provable from the checks; the registry treats the whole family as REAL_FIRESTORE either way.
4. READONLY_PROBE scripts (8) write only if the system under test is broken (negative probes: bogus ITN, demo-product checkout, empty verify-code). The scanner treats them as safe; a regression in the route would turn the probe into a write.
5. manual_only drops live coverage from the gate. For the CMS round trips this is by design (they are the live loop proof). For the ticketing and admin families, fixture replay would need an injected Firestore/Auth fake, which the repo already uses elsewhere (`FakeFirestore` in `reconcile-response-accuracy`); that is follow-up work, not part of this change.
